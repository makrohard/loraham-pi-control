# PLAN-G5 · DELTA 1 (handler, 2026-10-03 09:42Z) — the four corrections from the gate-1 plan review (VERDICT-PLAN-G5 1cb37775)

The base plan (plans/PLAN-G5.md) stands except for these points; they replace the corresponding text.

1. **ACK state machine — one valid ACK is required.** `apply_set` sends `SET key=value\n` and reads exactly ONE line (bounded, 1 s). Outcomes: line == `OK` → for a readable key the GET read-back decides `confirmed`; for an unconfirmable key the result is "SENT but UNCONFIRMED" (ok=True, confirmed=False). Line starts with `ERR` → ok=False, confirmed=False, reason = the sanitised, bounded ERR text, NO read-back. Anything else — timeout, empty line, a line that is neither `OK` nor `ERR` — → ok=False, confirmed=False, NO read-back (a GET that happens to show the value could show a pre-existing value). The docs/CHANGELOG sentence "no OK within 1 s fails" is therefore literally true.
2. **Timeout wording.** The read goes through the existing `RealUnixClient.request()` (connect + send + read in one call), so a `TimeoutError` or `OSError` does not prove the command was sent: never say "SENT" on that path; the detail is "SET unconfirmed — no valid OK within 1 s" / "SET not confirmed — <OSError class>" (not "unreachable" unless the connect itself failed, which `request()` does not distinguish — so do not claim it).
3. **Tests.** (a) `test_confirmable_key_without_valid_ack_is_not_applied`: a TXMODE SET whose reply is a timeout / empty / odd line while the fake's STATUS already shows the requested value → result not ok and not confirmed (red against the plan's original algorithm). (b) At least one principal ERR regression that is red on the BASE for the real defect: stub or monkeypatch the unix client so the fake daemon answers `ERR INVALID` with the base-compatible interface (not the new `set_replies=` keyword) → on base the old `send()` reports success (red), after the fix ok=False. The `set_replies=` tests stay as additional coverage.
